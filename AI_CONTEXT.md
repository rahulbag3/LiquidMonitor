Read this before changing anything. It describes only what is actually present in the code.

## 1. Project name and purpose

**LiquidMonitor v0.1** — a native Windows 11 floating network/system monitor prototype.

It is a small always-visible "overlay" style app: a compact pill showing live up/down
network speed, which expands into a dashboard with CPU / GPU / memory usage, ping,
adapter name, and two sparkline graphs. It is draggable, has a borderless rounded
window, and supports three visual themes.

Stated intent (from `README.md`): this is the foundation for a three-theme app
(Mica, Liquid Glass, Minimal). Version 0.1 = prototype.

## 5. Main classes and responsibilities

### `LiquidMonitor.App` (`App.xaml.cs`)
Minimal WinUI `Application`. Creates and activates the one `MainWindow`. Nothing else.

### `LiquidMonitor.MainWindow` (`MainWindow.xaml.cs`)
A `sealed partial class MainWindow : Window` holding **all** application logic.

**Window chrome / HWND**
- `ApplyWindowShape()` — sets `DWMWA_WINDOW_CORNER_PREFERENCE`, adds `WS_EX_LAYERED`, calls `DwmExtendFrameIntoClientArea` with all margins `-1` (layered window so rounded corners show).
- `ApplyRoundedWindowRegion()` / `ApplyRoundedCorners()` — both set the DWM corner attribute; effectively duplicates.
- `SetupWindow()` — gets `AppWindow` from the HWND, forces `IsResizable = false`, `SetBorderAndTitleBar(false, false)`, clears the title.
- `ResizeWindow(w, h)` — resizes via `AppWindow.Resize` (there is no user resize).
- `ToggleAlwaysOnTop()` — `SetWindowPos` with `HWND_TOPMOST` / `HWND_NOTOPMOST`.
- `SetInitialPosition()` — once only (`_initialPositionSet`); moves to the bottom-right of the work area with an 18px margin.

**Modes**
- `ShowCompact()` — `CompactCard` visible, `ExpandedCard` collapsed, resize to **250 x 52**.
- `ShowExpanded()` — the inverse, resize to **390 x 310**, then `UpdateGraphs()`.
- `_expanded` tracks the current mode.

**Input handling** (all on the `Root` Grid)
- `Root_PointerPressed` / `Root_PointerMoved` / `Root_PointerReleased` — custom drag via `GetCursorPos` + `AppWindow.Move`. State: `_dragging`, `_ignoreNextDrag`, `_mouseStart`, `_windowStart`, `_dragOffset`. Only the left button starts a drag; handlers set `e.Handled = true`.
- `Root_DoubleTapped` — toggles compact <-> expanded and sets `_ignoreNextDrag` so the double-click does not also start a drag.
- `Root_RightTapped` — shows a `MenuFlyout`.

**Timers**
- `_timer` — `DispatcherTimer`, **500 ms**, `Timer_Tick`.
- `_pingTimer` — `DispatcherTimer`, **5 s**, awaits `UpdateNetworkInfo()`.
- The `Closed` handler stops both timers and calls `PdhCloseQuery(_gpuQuery)` if open.

**Metric collection**
- `UpdateResourceUsage()` -> `UpdateCpuUsage()`, `UpdateMemoryUsage()`, `TryGetGpuUsage()`.
- `UpdateCpuUsage()` — `kernel32!GetSystemTimes` delta math; the first sample only primes `_lastCpuIdle`/`_lastCpuTotal` (`_cpuInitialized`).
- `UpdateMemoryUsage()` — `kernel32!GlobalMemoryStatusEx`, shows `MemoryLoad` percent.
- `InitializeGpuCounter()` / `TryGetGpuUsage(out double)` — PDH query on `\GPU Engine(*)\Utilization Percentage`, two-call buffer pattern, then the **max across all GPU engine instances**. Falls back to `"N/A"`.
- `GetNetworkTotals()` — static; picks the fastest `Up` non-loopback `NetworkInterface` (`OrderByDescending(n => n.Speed)`), returns `(BytesSent, BytesReceived)`.

**Rate computation**
- `Timer_Tick` — updates resources, gets totals, computes per-second up/down, **returns early on the first sample** (`_firstSample`), writes all four rate TextBlocks, pushes samples into history, redraws graphs only when `_expanded`.
- `AddSample(Queue<double>, double)` — caps each queue at `HistoryLength = 50`.
- `FormatRate(double)` — `B/s` -> `KB/s` -> `MB/s`.

**Graphs**
- `UpdateGraphs()` — no-ops when `GraphHost.ActualWidth/Height <= 0`; else `DrawDownload()` + `DrawUpload()`.
- `DrawDownload()` / `DrawUpload()` — rebuild `Polyline.Points` from history; `paddingTop = 10`, `paddingBottom = 12`, `max = history.Max() * 1.1`.
- `GraphHost_SizeChanged` -> `UpdateGraphs()`.
- `Draw(Polyline, Queue<double>)` — **dead code**, an older generic version using `* 1.08`.

**Network info**
- `UpdateNetworkInfo()` — `async`; pings `8.8.8.8` (2000 ms) into `PingText`, writes the adapter hardware name (`Description`, e.g. `Intel(R) Wi-Fi 6 AX201 160MHz`) into `AdapterText`, falling back to `Name` then the interface type. Failures degrade to `"Ping unavailable"`.

**Theming**
- `private enum ThemeMode { LiquidGlass, Material3, FrostedGlass }` — **there is no "Minimal" theme**, despite the README.
- `ApplyTheme(ThemeMode)` — assigns `Background`/`BorderBrush` on both cards plus `Root.Background`, then stores the mode in `_theme`.
- `CreateLiquidGlassBrush()` / `CreateMaterialCardBrush()` — build gradient brushes in code.
- Default theme is `LiquidGlass`.
- `TryEnableAcrylic()` — **dead code**; would set `SystemBackdrop = new DesktopAcrylicBackdrop()` but is never called.

**Interop declarations** (top of file)
- Structs: `POINT`, `NativeFileTime`, `MemoryStatus` (a `sealed class`, not a struct), `PdhFormattedValue` (`LayoutKind.Explicit`, `Size = 16`), `PdhFormattedItem`, `MARGINS`.
- Imports: `user32!GetCursorPos/SetWindowPos/SetWindowLong/GetWindowLong`, `kernel32!GetSystemTimes/GlobalMemoryStatusEx`, `pdh!PdhOpenQueryW/PdhAddEnglishCounterW/PdhCollectQueryData/PdhGetFormattedCounterArray/PdhCloseQuery`, `dwmapi!DwmExtendFrameIntoClientArea/DwmSetWindowAttribute`.
- Constants: `HWND_TOPMOST`, `HWND_NOTOPMOST`, `SWP_NOMOVE`, `SWP_NOSIZE`, `SWP_SHOWWINDOW`, `GWL_STYLE` (unused), `DWMWA_WINDOW_CORNER_PREFERENCE = 33`, `DWMWCP_ROUND = 2`, `GWL_EXSTYLE = -20`, `WS_EX_LAYERED = 0x00080000`.
- `ToUInt64(NativeFileTime)` — widens the FILETIME pair.

## 6. How the parts connect

```
App.OnLaunched
   └─> new MainWindow()          (constructor)
          ├─ InitializeComponent()          loads MainWindow.xaml
          ├─ WindowNative.GetWindowHandle()  caches _hwnd
          ├─ ApplyWindowShape() / ApplyRoundedWindowRegion()
          ├─ SetupWindow()                  AppWindow, non-resizable, no title bar
          ├─ InitializeGpuCounter()         opens the PDH query
          ├─ _timer (500ms)  ──> Timer_Tick ──> UpdateResourceUsage()  -> CPU/GPU/MEM TextBlocks + ProgressBars
          │                                   └─> GetNetworkTotals()   -> up/down rate TextBlocks
          │                                   └─> AddSample()          -> _upload/_downloadHistory
          │                                   └─> UpdateGraphs() (only if _expanded)
          ├─ _pingTimer (5s)   ──> UpdateNetworkInfo() -> PingText / AdapterText
          ├─ Closed            ──> stop both timers, PdhCloseQuery
          ├─ ApplyTheme(_theme)   -> card backgrounds + Root.Background
          └─ ShowCompact()        -> initial 250x52 state
```

**XAML <-> code-behind contract.** `MainWindow.xaml.cs` accesses these named
elements; renaming or removing any of them in XAML breaks the build:

`Root`, `CompactCard`, `ExpandedCard`, `CompactDownloadText`, `CompactUploadText`,
`DownloadText`, `UploadText`, `PingText`, `AdapterText`, `CpuUsageText`, `CpuUsageBar`,
`GpuUsageText`, `GpuUsageBar`, `MemoryUsageText`, `MemoryUsageBar`, `GraphHost`,
`DownloadGraph`, `UploadGraph`.

**Theming flow.** `MainWindow.xaml` declares brushes in `Grid.Resources`
(`AcrylicCardBrush`, `MaterialCardBrush`, `FrostedCardBrush`, `AcrylicBorderBrush`,
`MaterialBorderBrush`, `FrostedBorderBrush`, `GlassGlowBrush`) — but **`ApplyTheme`
does not read them**; it constructs new brushes in code. The XAML resources are
effectively unused, and the hard-coded `Background`/`BorderBrush` values in XAML are
overwritten at runtime by `ApplyTheme`.

**Input flow.** All pointer/right-click/double-tap handlers are wired on the root
`Root` `Grid` in `MainWindow.xaml`, not on individual elements. Children therefore
inherit the drag behaviour, and any new interactive child must be considered carefully.

## 7. Features already implemented

- **Compact mode** — floating pill (250x52) with `↓ download` and `↑ upload` rates,
  refreshed every 500 ms.
- **Expanded dashboard** (390x310) — large download/upload values, ping ms, adapter
  name, CPU / GPU / memory percentages with `ProgressBar`s, and two 50-sample
  sparkline graphs.
- **Toggle** — double-click anywhere on the window toggles compact/expanded.
- **Drag** — left-drag anywhere moves the window; initial position is bottom-right.
- **Right-click context menu** (`MenuFlyout`), in order:
  1. Compact Mode
  2. Expanded Mode
  3. Enable/Disable Always On Top (label reflects current state)
  4. separator
  5. Theme: Liquid Glass
  6. Theme: Material 3 Expressive
  7. Theme: Frosted Glass
  8. separator
  9. Close
- **Three themes** — Liquid Glass (default), Material 3 Expressive, Frosted Glass,
  all implemented as code-built gradient/solid brushes.
- **Always-on-top toggle** via `SetWindowPos`.
- **Live metrics** — CPU (`GetSystemTimes`), memory (`GlobalMemoryStatusEx`), GPU (PDH).
- **Network info** — ping to 8.8.8.8 and friendly adapter name.
- **Window chrome** — borderless, non-resizable, rounded corners, layered background.
- **Bounded history** — 50 samples per direction, so memory use is flat.
- **Graceful degradation** — GPU shows `N/A`, ping shows `Ping unavailable`; no
  exceptions escape the timer callbacks.

## 8. Known issues and unfinished features

### 8.1 RESOLVED — two separate startup crashes

The project **builds cleanly** and the app **now runs**. There were **two independent**
causes, both in startup. They are recorded here because the earlier note blamed the wrong
thing entirely.

#### 8.1a FIXED — the Windows App SDK bootstrap was never initialised

This caused the `REGDB_E_CLASSNOTREG` crash. The SDK only auto-enables its bootstrap when
**both** of these hold (see `Microsoft.WindowsAppSDK.BootstrapCommon.targets` in the
`microsoft.windowsappsdk.foundation` package):

```xml
'$(WindowsAppSDKSelfContained)' != 'true'  AND  '$(WindowsPackageType)' == 'None'
```

The project set `WindowsAppSDKSelfContained=true` **and** `EnableMsixTooling=true`, so
**both** conditions failed and no bootstrap was injected — the XAML framework was never
registered.

Fix in `LiquidMonitor.App.csproj`:

```xml
<WindowsAppSdkBootstrapInitialize>true</WindowsAppSdkBootstrapInitialize>
<WindowsAppSdkDeploymentManagerInitialize>false</WindowsAppSdkDeploymentManagerInitialize>
<WindowsAppSdkUndockedRegFreeWinRTInitialize>false</WindowsAppSdkUndockedRegFreeWinRTInitialize>
```

`DeploymentManager` must be disabled: when auto-injected into an **unpackaged** app it
throws `InvalidOperationException: The process has no package identity`, killing startup
on its own.

#### 8.1b FIXED — `ProgressBar` crashes the XAML framework on this runtime

Even with the bootstrap fixed the app still died (`0xC000027B`, WER bucket
`combase.dll` / `802b000a` `COR_E_EXECUTIONENGINE`) with `MainWindowHandle == 0`, i.e. the
window was never created.

Isolated by building a minimal WinUI app with an **identical csproj, assembly name and
namespace** and swapping in one XAML file at a time:

| XAML content | Result |
|---|---|
| `TextBlock` only | STABLE |
| `Canvas` + `Polyline` | STABLE |
| `Button`, `Slider` (also templated) | STABLE |
| **`ProgressBar` (single element)** | **CRASH** |

A single `<ProgressBar/>` on its own was enough to kill the process, even with an explicit
`ControlTemplate` (so it is not a `generic.xaml` lookup problem — it is the control's
activation itself). This is specific to `ProgressBar` on the installed Windows App Runtime
2.5.1 and is **not** a general WinUI 3 defect.

**Fix:** the three usage bars are now `Border` elements sized by a `SetBar(Border, double)`
helper in `MainWindow.xaml.cs`, which computes `Width = track * (percent / 100)` from the
parent's `ActualWidth`. The `CpuUsageBar` / `GpuUsageBar` / `MemoryUsageBar` `x:Name`s are
unchanged, but their **type changed** from `ProgressBar` to `Border`, so code-behind must
use `SetBar(...)` rather than `.Value`.

#### 8.1c Also fixed — malformed 9-digit ARGB colours

`MainWindow.xaml` had `Background="#CC10151FFF"` on both card `Border`s — **nine** hex
digits (should be eight). Corrected to `#CC10151F`. Verified that `#CC10151F` is stable
while `#CC10151FFF` crashes.

#### 8.1d Superseded note

An earlier revision claimed `WindowsAppSDKSelfContained=true` "made the exe no longer
crash immediately" and offered it as the fix. That was a false positive: self-contained
mode only changes *which* failure you get (`0xC000027B` vs `0xE0434352`); it never made
the app start.

### 8.2 Documentation drift

- `README.md` says "Windows App SDK 2.5.1"; the csproj references `1.6.250402001`.
- `README.md` advertises a "Native Mica backdrop". There is **no Mica code** anywhere.
  The only backdrop code is `TryEnableAcrylic()`, which sets a `DesktopAcrylicBackdrop`
  and is **never called** — `SystemBackdrop` is never assigned anywhere.
- `README.md` says the themes are "Mica, Liquid Glass, and Minimal". The actual
  `ThemeMode` enum is `LiquidGlass`, `Material3`, `FrostedGlass`. There is no "Minimal".
- The generated `AppxManifest.xml` depends on `Microsoft.WindowsAppRuntime.1.6`,
  further confirming 1.6 rather than 2.5.1.

### 8.3 Dead / unused code

- `TryEnableAcrylic()` — never called.
- `Draw(Polyline, Queue<double>)` — superseded by `DrawDownload()`/`DrawUpload()`.
- `ApplyRoundedCorners()` — duplicate of `ApplyRoundedWindowRegion()`.
- `GWL_STYLE` constant — unused.
- All seven brushes in `MainWindow.xaml`'s `Grid.Resources` — `ApplyTheme` builds its
  own brushes in code instead of consuming them.

### 8.4 Packaging gaps

- No `Assets/` folder in source, yet the auto-generated `AppxManifest.xml` references
  `Assets\StoreLogo.png`, `Assets\Square150x150Logo.png` and `Assets\Square44x44Logo.png`.
  MSIX packaging/signing will likely fail until these exist.
- No source `Package.appxmanifest`; packaging depends entirely on `EnableMsixTooling`
  auto-generation.

### 8.5 Correctness / robustness concerns

- **GPU counter path** uses `PdhAddEnglishCounterW` with the English counter name
  `\GPU Engine(*)\Utilization Percentage`. On a non-English Windows this can fail and
  permanently show `N/A`. The value is the max across all engine instances, an
  approximation rather than true total GPU load.
- **Network adapter selection** picks one adapter by `Speed` and never re-evaluates it.
  If the active adapter changes, the byte counters jump and a huge bogus rate is shown.
  VPN/virtual adapters may also win the `OrderByDescending(Speed)` comparison.
- **Hard-coded graph clip**: `Canvas.Clip` is `RectangleGeometry Rect="0,0,380,90"`,
  which does not track the real `GraphHost` size.
- **First tick shows nothing** — `Timer_Tick` returns early on `_firstSample`, so rates
  are blank for the first 500 ms.
- **CPU** is busy-time delta over wall time, so it is overall CPU utilisation, not a
  per-core figure.
- **No persistence**: theme, always-on-top and window position are not saved between runs.
- **No tests, no CI, no logging or diagnostics.**
- `MainWindow.xaml.cs` is ~1213 lines with everything in one file; there is no separation
  between metric collection, window management and rendering.

### 8.6 Missing product features

No tray icon, no start-up registration, no settings UI, no per-adapter selection,
no total/session data, no localisation.

## 10. Rules for future modifications

Treat these as constraints. Breaking any of them is a regression even if the build
still succeeds.

**Build and platform**
1. Build with `powershell -ExecutionPolicy Bypass -File .\build.ps1`. There is no test
   suite, so a successful x64 build plus a manual launch check *is* the verification.
2. Do not change `Platforms`/`PlatformTarget`/`RuntimeIdentifier` away from x64/win-x64,
   or `TargetFramework`/`TargetPlatformMinVersion` away from `net8.0-windows10.0.22621.0`
   / `10.0.22621.0`, without an explicit reason. The solution only defines
   `Debug|x64` and `Release|x64`.
3. Do not break the MSIX deployment path: `EnableMsixTooling=true` and
   `launchSettings.json` (`commandName: MsixPackage`) are what Visual Studio F5 relies on.
4. There are no third-party NuGet packages today. Adding one requires network restore;
   confirm that is acceptable before doing it.

**XAML / code-behind contract**
5. Never rename or remove the `x:Name` elements listed in section 6 without updating
   `MainWindow.xaml.cs` in the same change. The code-behind is the consumer; XAML alone
   is not the source of truth for theming.
6. `ApplyTheme` overwrites `Root.Background`, `CompactCard.Background`,
   `CompactCard.BorderBrush`, `ExpandedCard.Background` and `ExpandedCard.BorderBrush`.
   Hard-coding those in XAML has no lasting effect. If you move theming into
   `App.xaml` resources, change `ApplyTheme` in the same change.
7. The `Root` `Grid` is the single input surface for drag, double-click and right-click.
   Adding a child control that handles its own pointer events will conflict with the
   window-drag logic; check the `e.Handled` handling before adding interactive children.
8. When changing layout size, update `ShowCompact()` (250x52), `ShowExpanded()` (390x310),
   the `ResizeWindow` calls, and the hard-coded `Canvas.Clip` rect together.

**Runtime / resource lifetime**
9. Any new timer or async loop must be stopped in the `Closed` handler, which already
   stops `_timer`/`_pingTimer` and calls `PdhCloseQuery`.
10. Any new PDH query or unmanaged allocation must be released. `TryGetGpuUsage` uses the
    two-call `PdhGetFormattedCounterArray` size-then-data pattern with
    `Marshal.AllocHGlobal`/`FreeHGlobal` in a `finally` — copy that pattern exactly.
11. Do not alter the `[StructLayout]` attributes or field order of `POINT`,
    `NativeFileTime`, `MemoryStatus`, `PdhFormattedValue` (explicit, `Size = 16`),
    `PdhFormattedItem` or `MARGINS`. They mirror native layouts; changing them silently
    corrupts marshalled data. `MemoryStatus` must stay a `sealed class` because
    `GlobalMemoryStatusEx` takes it `[In, Out]`.
12. `HistoryLength = 50` is referenced by `AddSample` and the graph maths. Keep the queue
    cap and the graph drawing consistent if you change it.

**Behaviour that is intentional — do not "fix" it without asking**
13. `GetSystemTimes` CPU maths is a busy-time delta (overall utilisation, not per-core).
14. GPU utilisation is the max across `\GPU Engine(*)` instances, not a total.
15. The English PDH counter name is a deliberate localisation workaround; do not replace
    it with a localised name.
16. The 500 ms and 5 s timer intervals, and the numeric thresholds, are product choices.

**Style**
17. Nullable reference types are enabled; annotate new members accordingly and match the
    existing nullable-annotation style.
18. `MainWindow.xaml.cs` uses heavily blank-line-separated, one-statement-per-line
    formatting. Match it rather than reformatting the file.
19. `LiquidMonitor.App.csproj` is saved with a UTF-8 BOM. Preserve the encoding when
    editing it.
20. Prefer small, additive, verifiable changes. This is a single-window prototype with all
    logic in one file — a large refactor should be proposed, not performed unasked.
21. Keep this file (`AI_CONTEXT.md`) accurate: update it whenever the stack, structure,
    the `x:Name` contract, or the known-issues list changes.
